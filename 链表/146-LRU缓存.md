# 146 LRU 缓存

- 难度：中等
- 标签：**设计**、**哈希表**、**链表**、**双向链表**
- 力扣链接：https://leetcode.cn/problems/lru-cache/?envType=study-plan-v2&envId=top-100-liked

> 说明：本题参考力扣官方题解「LRU缓存机制」（slug：`lruhuan-cun-ji-zhi-by-leetcode-solution`）。正文主解是 **哈希表 + 双向链表**（官方方法一），get/put 平均时间都是 O(1)，是 LRU 这类设计题的经典写法。面试官一般会期望读者**自己手写一个简单的双向链表**，而不是直接用语言自带的封装数据结构（如 C++ 的 `std::list`、Java 的 `LinkedHashMap`、Python 的 `OrderedDict`），所以本题的代码量比一般题大。

## 题目描述

请你设计并实现一个满足 LRU (最近最少使用) 缓存 约束的数据结构。

实现 `LRUCache` 类：

- `LRUCache(int capacity)` 以 正整数作为容量 `capacity` 初始化 LRU 缓存
- `int get(int key)` 如果关键字 `key` 存在于缓存中，则返回关键字的值，否则返回 `-1` 。
- `void put(int key, int value)` 如果关键字 `key` 已经存在，则变更其数据值 `value` ；如果不存在，则向缓存中插入该组 `key-value` 。如果插入操作导致关键字数量超过 `capacity` ，则应该**逐出最久未使用**的关键字。

函数 `get` 和 `put` 必须以 **O(1)** 的平均时间复杂度运行。

**示例：**

```
输入
["LRUCache", "put", "put", "get", "put", "get", "put", "get", "get", "get"]
[[2], [1, 1], [2, 2], [1], [3, 3], [2], [4, 4], [1], [3], [4]]
输出
[null, null, null, 1, null, -1, null, -1, 3, 4]

解释
LRUCache lRUCache = new LRUCache(2);
lRUCache.put(1, 1); // 缓存是 {1=1}
lRUCache.put(2, 2); // 缓存是 {1=1, 2=2}
lRUCache.get(1);    // 返回 1
lRUCache.put(3, 3); // 该操作会使得关键字 2 作废，缓存是 {1=1, 3=3}
lRUCache.get(2);    // 返回 -1 (未找到)
lRUCache.put(4, 4); // 该操作会使得关键字 1 作废，缓存是 {4=4, 3=3}
lRUCache.get(1);    // 返回 -1 (未找到)
lRUCache.get(3);    // 返回 3
lRUCache.get(4);    // 返回 4
```

**提示：**

- `1 <= capacity <= 3000`
- `0 <= key <= 10000`
- `0 <= value <= 10^5`
- 最多调用 `2 * 10^5` 次 `get` 和 `put`

> 关于接口：本题要实现的是一个 `LRUCache` 类（不是普通的 `Solution` 类），包含构造函数 `LRUCache(int capacity)`、`get(int key)`、`put(int key, int value)` 三个方法。注意 `get` 不存在要返回 `-1`，`put` 满了要淘汰最久未使用的那一项。调用次数最高达 `2*10^5`，所以 `get`/`put` 必须是 O(1)，任何 O(n) 的查找都会超时。

## 思路

> 本题主要参考力扣官方题解的「方法一：哈希表 + 双向链表」。

### LRU 是什么？要淘汰谁？

LRU = **Least Recently Used**（最近最少使用）。它的核心规则只有一条：**当缓存满了要淘汰时，把「最久没被碰过」的那一项扔掉**。

这模拟的是「最近用过的东西大概率还会再用」的直觉——你桌上最近翻过的书放最上面，好久没碰的书被压到最底下，桌满了就先清理最底下的。所以 LRU 需要维护一个**访问顺序**：

- 每次 `get(key)` 或 `put(key, value)`，这个 key 就变成「最近被用过」，要挪到顺序的**最前**；
- 长期不被访问的 key 会慢慢沉到顺序的**最后**；
- 容量满时，直接淘汰**最后**那个（最久未使用）。

### 为什么需要双向链表？

因为「挪到最前」和「淘汰最后」都要 **O(1)**。

- **链表头/尾的插入删除** 本来就是 O(1)（改几个指针就行），比数组（要整体挪元素 O(n)）强。
- 但 LRU 的关键操作是「把链表中间的某个节点挪到头部」——这要求能 **O(1) 把一个节点从链表里摘下来**。

摘一个中间节点 `node`，需要把它的**前驱**和**后继**接起来：

```
node->prev->next = node->next;
node->next->prev = node->prev;
```

这要求 `node` 自己记得 `prev`（前驱）是谁。**单向链表做不到**——它只有 `next`，找前驱只能从头遍历，O(n)。双向链表每个节点同时存 `prev` 和 `next`，摘节点 O(1)。

所以选 **双向链表** 维护访问顺序：头部 = 最近使用，尾部 = 最久未使用。

### 为什么需要哈希表？

双向链表能 O(1) 摘节点，但前提是**你已经拿到了那个节点的指针**。`get(key)` 给的是一个 `int key`，怎么在链表里找到它对应的节点？遍历一遍是 O(n)，不行。

**哈希表** `unordered_map<int, DLinkedNode*>` 解决这个问题：`key → 节点指针`，O(1) 查到节点在哪。

两者一配合：

| 数据结构 | 作用 | 复杂度 |
|---|---|---|
| 哈希表 `cache` | 由 `key` O(1) 定位到节点指针 | O(1) 查找 |
| 双向链表 | 维护访问顺序，O(1) 摘/插节点 | O(1) 增删 |

`get` = 哈希表查节点 → 链表里挪到头部；`put` = 哈希表查在不在 → 链表头插（满了再删尾）。全程 O(1)。

### 为什么用哨兵 head/tail（伪头部、伪尾部）？

双向链表的「头插」「删尾」会频繁碰到**边界**：插第一个节点时，`head` 概念还不存在；删最后一个节点时，`tail` 的前驱可能是空。如果每次操作都要 `if (head == nullptr)` 判一下，代码会变得很啰嗦、很容易写错。

**哨兵节点（dummy head / dummy tail）**：一开始就 `new` 两个**不存真实数据**的节点 `head` 和 `tail`，让它们互指：

```
head ⇄ tail     （初始，中间没有任何真实节点）
```

之后所有真实节点都插在 `head` 和 `tail` **之间**。这样：

- **头部插入** 永远是「插在 `head` 后面」，`head` 一定存在，不用判空；
- **尾部删除** 永远是「删 `tail->prev`」，`tail` 一定存在，`tail->prev` 至少是 `head`，也不用判空；
- 节点的 `prev`/`next` 永远不会是 `nullptr`（两端被哨兵挡住），避免空指针特判。

代价只是多两个 dummy 节点的内存，几乎可以忽略，换来的是**所有指针操作无需任何边界特判**，写起来又稳又短。

### get 和 put 的具体操作

- **`get(key)`**：
  1. 哈希表查 `key` 在不在；不在直接返回 `-1`。
  2. 在：拿到节点指针，把它**挪到头部**（`moveToHead`），返回它的 `value`。
     ——「挪到头部」= 先从链表摘下来（`removeNode`），再头插（`addToHead`）。

- **`put(key, value)`**：
  1. 哈希表查 `key` 在不在。
  2. **不在**：`new` 一个新节点 → 存进哈希表 → 头插到链表 → `size++`。如果 `size > capacity`：删尾部节点（`removeTail`）→ 从哈希表删对应项 → `delete` 释放内存 → `size--`。
  3. **在**：拿到节点，**更新 `value`**，再挪到头部。（注意是「更新值 + 提到头部」，**不**新增节点、**不**淘汰。）

> **注意 put 已存在 key 的处理**：很多人第一反应是「先删再插」，但官方写法更省事——直接改 `node->value`，再 `moveToHead`。因为节点已经在哈希表和链表里了，没必要删了重建。

### 手动推导示例（capacity = 2）

跟踪官方示例，链表用 `head ⇄ ... ⇄ tail` 表示，**左边靠近 head = 最近用过**：

```
构造 LRUCache(2)：head ⇄ tail，size=0

put(1,1)：key=1 不存在
  → new 节点(1,1)，cache[1]=节点，addToHead
  → 链表：head ⇄ (1,1) ⇄ tail，size=1
  → 不超容量，不淘汰

put(2,2)：key=2 不存在
  → new 节点(2,2)，cache[2]=节点，addToHead
  → 链表：head ⇄ (2,2) ⇄ (1,1) ⇄ tail，size=2
  → 不超容量，不淘汰

get(1)：key=1 在
  → moveToHead((1,1))：先摘掉 (1,1)，再头插
  → 链表：head ⇄ (1,1) ⇄ (2,2) ⇄ tail
  → 返回 1              （(1,1) 现在最靠头，(2,2) 沉到尾部附近）

put(3,3)：key=3 不存在
  → new 节点(3,3)，头插
  → 链表：head ⇄ (3,3) ⇄ (1,1) ⇄ (2,2) ⇄ tail，size=3 > 2
  → 超容量！removeTail 摘掉 tail->prev=(2,2)
  → cache.erase(2)，delete 节点，size=2
  → 链表：head ⇄ (3,3) ⇄ (1,1) ⇄ tail
  → 被淘汰的是 (2,2)，因为它最久没被碰（get(1) 把 1 提到前面了）

get(2)：key=2 不在（刚被淘汰）→ 返回 -1

put(4,4)：key=4 不存在
  → new 节点(4,4)，头插
  → 链表：head ⇄ (4,4) ⇄ (3,3) ⇄ (1,1) ⇄ tail，size=3 > 2
  → removeTail 摘掉 (1,1)，cache.erase(1)，size=2
  → 链表：head ⇄ (4,4) ⇄ (3,3) ⇄ tail

get(1)：不在 → -1
get(3)：在 → moveToHead → 返回 3
get(4)：在 → moveToHead → 返回 4
```

可以看到 LRU 的精髓：**谁被访问（get 或 put），谁就被提到头部；满时淘汰 tail 前面那个（最久未访问）**。整个顺序是动态的，靠双向链表的 O(1) 增删维护。

## 代码

```cpp
// ============ ① 双向链表节点结构 ============
// 每个节点存：key、value、前驱指针 prev、后继指针 next。
//   - 注意要存 key！不只是 value。因为淘汰尾部节点时，
//     要根据被删节点的 key 去哈希表里删对应项，节点自己必须记得 key。
struct DLinkedNode {
    int key, value;
    DLinkedNode* prev;     // 前驱：指向前一个节点（双向链表比单向多这一根）
    DLinkedNode* next;     // 后继：指向下一个节点
    // 默认构造：key/value 都 0，两根指针置空。给哨兵 head/tail 用。
    DLinkedNode() : key(0), value(0), prev(nullptr), next(nullptr) {}
    // 带参构造：给真实数据节点用，存入 key 和 value。
    DLinkedNode(int _key, int _value)
        : key(_key), value(_value), prev(nullptr), next(nullptr) {}
};

class LRUCache {
private:
    // ============ ③ 哈希表：key → 节点指针 ============
    // unordered_map<int, DLinkedNode*>：C++ STL 哈希表。
    //   - key 类型 int（缓存里的 key），value 类型 DLinkedNode*（指向链表节点的指针）。
    //   - 含义：由 key 在 O(1) 时间内定位到对应的链表节点。
    //   - 查找/插入/删除均摊 O(1)（比 map 的 O(log n) 快，本题要求 O(1) 必须用它）。
    //   - 用裸指针做 value 没问题，但要注意：节点 new 出来后必须手动 delete，否则内存泄漏。
    unordered_map<int, DLinkedNode*> cache;

    // 哨兵头/尾：不存真实数据，只是占位，避免边界特判。
    //   - 真实节点永远夹在 head 和 tail 之间。
    DLinkedNode* head;
    DLinkedNode* tail;
    int size;        // 当前缓存里真实节点的数量（不含哨兵）
    int capacity;    // 容量上限

public:
    // 构造函数：初始化容量、size=0，并创建两个哨兵节点互指。
    //   - 成员初始化列表 capacity(_capacity), size(0)：在进入函数体前就赋好值，比在函数体里赋值高效。
    LRUCache(int _capacity) : capacity(_capacity), size(0) {
        head = new DLinkedNode();   // 伪头部
        tail = new DLinkedNode();   // 伪尾部
        head->next = tail;          // head 的后继指向 tail
        tail->prev = head;          // tail 的前驱指向 head
        // 此时链表：head ⇄ tail，中间没有任何真实节点。
    }

    // ============ get：O(1) ============
    int get(int key) {
        // cache.count(key)：返回哈希表里 key 的个数（0 或 1）。
        //   - 用 count 判断「在不在」是惯用法，不会像 cache[key] 那样偷偷插入。
        if (!cache.count(key)) {
            return -1;              // 不存在，按题意返回 -1
        }
        // key 存在：先通过哈希表 O(1) 拿到节点指针，
        //           再把它挪到头部（表示「刚被用过」）。
        DLinkedNode* node = cache[key];
        moveToHead(node);
        return node->value;
    }

    // ============ put：O(1) ============
    void put(int key, int value) {
        if (!cache.count(key)) {
            // —— key 不存在：新建节点插入 ——
            DLinkedNode* node = new DLinkedNode(key, value);
            cache[key] = node;      // 存进哈希表
            addToHead(node);        // 头插到链表
            ++size;
            if (size > capacity) {
                // 超容量：淘汰最久未使用（尾部节点）
                DLinkedNode* removed = removeTail();
                cache.erase(removed->key);  // 从哈希表删对应项（用节点的 key）
                delete removed;              // 释放内存，防止内存泄漏
                --size;
            }
        } else {
            // —— key 已存在：更新 value，并提到头部（注意不新增节点、不淘汰）——
            DLinkedNode* node = cache[key];
            node->value = value;    // 直接改值
            moveToHead(node);       // 提到头部
        }
    }

private:
    // ============ ② 双向链表的四个指针操作辅助函数 ============

    // addToHead：把 node 插到伪头部 head 的后面（成为新的「最近使用」）。
    // 初始：head ⇄ oldNext  （oldNext 可能是 tail，也可能是原来的第一个真实节点）
    // 目标：head ⇄ node ⇄ oldNext
    void addToHead(DLinkedNode* node) {
        node->prev = head;          // node 的前驱指向 head
        node->next = head->next;    // node 的后继指向 head 原来的下一个（oldNext）
        head->next->prev = node;    // oldNext 的前驱改指向 node
        head->next = node;          // head 的后继改指向 node
        // 顺序要点：先让 node 抓住两端（前两句），再去改 head->next 和 oldNext->prev。
        //   - 因为 head->next 一旦被改，oldNext 就只能通过 node->next 找到了，
        //     所以第三句「head->next->prev = node」必须在「head->next = node」之前执行。
    }

    // removeNode：把 node 从链表里摘下来（不 delete，只是断开链接）。
    // 目标：node->prev ⇄ node ⇄ node->next  →  node->prev ⇄ node->next
    void removeNode(DLinkedNode* node) {
        node->prev->next = node->next;   // 前驱的后继 跳过 node 指向后继
        node->next->prev = node->prev;   // 后继的前驱 跳过 node 指向前驱
        // node 自己的 prev/next 没清空，但无所谓——它要么马上被 addToHead 重新接上，
        //   要么马上被 delete，不会再被遍历到。
    }

    // moveToHead：把一个已存在的节点挪到头部 = 先摘下来 + 再头插。
    //   - get 和 put（key 已存在）都用它表示「刚被访问」。
    void moveToHead(DLinkedNode* node) {
        removeNode(node);
        addToHead(node);
    }

    // removeTail：淘汰尾部节点 = 摘掉 tail 的前驱（最久未使用），并返回它（外面要 delete + 清哈希表）。
    DLinkedNode* removeTail() {
        DLinkedNode* node = tail->prev;   // 尾部真实节点 = tail 的前驱
        removeNode(node);                  // 摘下来
        return node;                       // 返回给调用者去 delete 和 cache.erase
    }
};
```

## 复杂度

- **时间**：`get` 和 `put` 都是 **O(1)**（平均）。
  - 哈希表的 `count` / `[]` / `erase` 都是均摊 O(1)；
  - 双向链表的 `addToHead` / `removeNode` / `moveToHead` / `removeTail` 都只改常数个指针，O(1)。
  - 这正是题目「必须以 O(1) 平均时间复杂度运行」的硬性要求。
- **空间**：**O(capacity)**。
  - 哈希表和双向链表最多存 `capacity` 个真实节点 + 2 个哨兵节点。官方说法是「最多存储 `capacity + 1` 个元素」（因为 put 新节点时先插入再判断超容量，会瞬时多一个，但马上被删）。

## 疑惑 / 卡点

> 这块记录做题时和 AI 的问答，方便以后回顾。随做题提问持续更新。

### Q1：为什么用双向链表，不能用单向链表？

因为 LRU 要 **O(1) 把链表中间的某个节点摘下来**（`moveToHead` 的第一步）。

摘一个节点 `node`，必须把它的**前驱**和**后继**直接接起来：

```cpp
node->prev->next = node->next;
node->next->prev = node->prev;
```

这要求 `node` 自己记得前驱是谁。**单向链表只有 `next`**，要找 `node` 的前驱只能从头遍历，O(n)。调用次数最高 `2*10^5`，O(n) 会超时。

双向链表每个节点同时存 `prev` 和 `next`，摘节点 O(1)。所以必须双向。

### Q2：哨兵节点（伪头部/伪尾部）为什么必要？

为了**免去边界特判**，让所有指针操作统一。

不用哨兵的话，插第一个节点时要判 `head == nullptr`、删最后一个节点时要判尾节点是不是空、`node->prev` 可能是空……每一处都要写 `if`，代码又长又容易漏。

加了哨兵 `head` 和 `tail`（一开始互指），真实节点永远夹在中间：

- 头插永远是「插在 `head` 后面」，`head` 一定在；
- 删尾永远是「删 `tail->prev`」，`tail` 一定在；
- 真实节点的 `prev`/`next` 永远不会是空（被哨兵挡住）。

代价只是 2 个 dummy 节点的内存，换来代码里**一个 `if` 都不用写**。这是链表设计题的通用技巧。

### Q3：`addToHead` 里四句指针赋值的顺序能换吗？

**部分能换，但有约束**。核心原则：**先让新节点 `node` 抓住两端，再去改 `head->next` 和 `oldNext->prev`**。

官方写法：

```cpp
node->prev = head;          // ① node 抓 head
node->next = head->next;    // ② node 抓 oldNext（此时 head->next 还没改，能拿到 oldNext）
head->next->prev = node;    // ③ oldNext 抓 node（等价于 head->next->prev，因为此时 head->next 还是 oldNext）
head->next = node;          // ④ head 抓 node
```

关键：**②必须在④之前**。因为 ② 要通过 `head->next` 拿到 `oldNext`，如果先执行 ④ 把 `head->next` 改成 `node`，就再也找不到 `oldNext` 了（除非你另存一个临时变量）。

同理 **③ 必须在 ④ 之前**，因为 ③ 里的 `head->next->prev` 此时还得是 `oldNext->prev`。

记不住顺序的话，背一句口诀：**「新节点先认两边，旧邻居再认新节点」**，或者干脆用临时变量 `DLinkedNode* nxt = head->next;` 把 `oldNext` 存出来再随便改顺序。

### Q4：`put` 时 key 已经存在，为什么不删了重建、而是直接改值？

因为节点已经在哈希表和链表里了，**没必要浪费一次 `delete` + `new`**。直接：

```cpp
node->value = value;    // 改值
moveToHead(node);       // 提到头部
```

省掉了：`new` 一个新节点、`delete` 旧节点、改哈希表项。逻辑等价但更高效、更简洁。

注意此时**不增 size、不触发淘汰**——节点数量没变，只是值变了、位置挪了。

### Q5：节点为什么要存 `key`，不只存 `value`？

因为**淘汰尾部节点时要反过来去哈希表删对应项**。`removeTail` 返回的是节点指针，外面要执行 `cache.erase(removed->key)`——如果节点不存 `key`，就没法知道该删哈希表里的哪一项。

所以双向链表节点的字段是 `{key, value, prev, next}`，比普通链表节点（只有 `val, next`）多一个 `key` 和一个 `prev`。

## 复盘

- **核心套路：「哈希表 + 双向链表 = O(1) 的 LRU」是经典设计模式**。哈希表负责 O(1) 定位，双向链表负责 O(1) 维护顺序，哨兵节点省掉边界特判。这套组合是工业界 LRU 实现（如 Redis 的 LRU 淘汰、Linux 内核的 LRU 链表）的内核写法，面试也是标准答案。
- **可迁移到 LFU**：「460 LFU 缓存」是同类设计题（淘汰「最不常用」而非「最久未用」），同样要哈希表 + 链表，只是链表维护的是「访问频次」而不是「访问时间」。把 146 的双向链表骨架吃透，460 就只剩「如何按频次分组」这一层新东西。
- **关键记忆点**：
  1. **节点存 `{key, value, prev, next}`**——`key` 是为了淘汰时反查哈希表。
  2. **两个哨兵 `head`/`tail` 互指**——所有指针操作零特判。
  3. **四个辅助函数**：`addToHead`（头插）、`removeNode`（摘节点）、`moveToHead`（= remove + add）、`removeTail`（淘汰）。
  4. **put 已存在 key = 改值 + moveToHead**，不新增不淘汰。
  5. **指针赋值顺序**：「新节点先认两边，旧邻居再认新节点」。
- **易错点**：
  - 忘了 `delete` 被淘汰的节点 → 内存泄漏（力扣看不出来，工程里是大坑）。
  - 忘了 `cache.erase(removed->key)` → 哈希表残留指向已释放内存的指针（悬挂指针）。
  - `addToHead` 指针顺序写错 → 链表断开或成环。
- **语言自带的「懒人」替代**（仅了解，面试别用）：C++ 可用 `std::list<pair<int,int>>` + 哈希表存迭代器；Java 的 `LinkedHashMap` 设 `accessOrder=true` 重写 `removeEldestEntry` 即可；Python 的 `OrderedDict` 有 `move_to_end` 和 `popitem(last=True)`。这些能几行 AC，但本题考查的就是手写双向链表，别走捷径。
